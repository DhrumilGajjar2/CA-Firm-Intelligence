Note 1 (updated 2026-11-22, P1 slice 3): **Passed for every firm-scoped P1 endpoint** (`/auth/me`, `/firms/current` and settings, `/users`, `/users/invite`,
`/users/:id`, `/users/:id/role`, `/users/:id/status`, `/invitations`, `/invitations/:id`, `/auth/invitations/:token`, `/auth/accept-invitation`).
Evidence: `tenant-isolation-slice3.test.ts` (27 tests, THREE firms with all four roles each): lists, counts, `meta.total`, search and filters never include
another firm's rows (ids, emails, names and firm ids are searched for in every body); another firm's user or invitation id is `404` for every role
(owner `404`; on owner-only routes the other roles are stopped by the `403` role check first) with a body byte-identical to an unknown id, and a byte-for-byte
snapshot of the other firms' rows is unchanged afterwards; smuggled `firm_id`/`id`/`role: "owner"`/`is_active`/`invited_by_id` in body, query and headers are ignored
(the row lands in the caller's firm); forged sessions mixing firms are `401` on all ten endpoints; invitation tokens are bound to their own invitation (firm B's token
gives firm B membership and the invited role only; one email invited by three firms and accepted at once gives one `201` and two `409`); changes in one firm never
touch another firm's same-named users or sessions. Earlier slices (`firms.test.ts`, `firms-adversarial.test.ts`, `auth-session-attacks.test.ts`, `users.test.ts`,
`invitations.test.ts`) cover the firm endpoints and a second angle on users/invitations. Live check against a real server on port 5058: firm B's owner gets `404` for
firm A's user (GET, PATCH, role, status) and invitation (DELETE) and sees only its own users and invitations. Not yet applicable: clients, services, engagements,
imports and finance (P2-P4): the same checks must be repeated for each.

Note 10 (updated 2026-11-22, P1 slice 3): **Passed for every P1 endpoint.** Expired, not-yet-valid, tampered, wrong-secret, `alg:none`, algorithm-confusion, malformed-claim
(P1-002, closed), deleted-user, deleted-membership, inactive-membership and cross-firm tokens are `401` with the standard envelope on the auth and firm endpoints (slices 1-2)
and on all users/invitations endpoints (`slice3-rbac-matrix.test.ts`, `tenant-isolation-slice3.test.ts`). Deactivation is felt on the very next request with the old cookie
on every authenticated endpoint at once (`401`, and `401` wins over `403` for a deactivated user); reactivation restores it; role changes move permissions both ways at once;
the database role beats a token that claims `owner`. The UI half (P1-008: a `401` answering a save or any team mutation sends the user to `/login?next=`, auth-form `401`s do
not) is verified at component level in `p1-008-reverify.test.tsx` (16 tests); a real browser was not used.

**Observations (not logged as bugs; confirm they are accepted)**

- JWTs are stateless: after `POST /auth/logout`, a copy of the old cookie stays valid until it expires (8 h) or the membership is
  deactivated. The contract only promises "clears the cookie". Likewise sessions survive a password reset (already parked as P1 decision 9).
- In non-production the dev mailer writes the reset URL (with the raw token) to the server log by design (P1 decision 5). The logs test
  runs in production mode, where nothing is logged.
- Login and register have no rate limiting (parked to P4, decision 9).
- `@fastify/cors` with a fixed origin answers every request with `Allow-Origin: <FRONTEND_URL>` even for foreign origins; this is safe
  because browsers compare it with the requesting origin.
- Success responses carry no `Cache-Control: no-store` (not specified in the contract; not assessed further).
